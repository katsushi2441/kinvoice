# 実際に踏んだ6つの罠

このシステムは1日で作りましたが、その途中で6回つまずいています。
**すべて実際に起きたことで、作り話は入っていません。**

バイブコーディングで本当に難しいのは、コードを書くことではありません。
**「動いたように見えて動いていない」を見抜くこと**です。以下はその実例です。

---

## 罠1. メールが「送信済」なのに届いていない

### 何が起きたか

領収書を発行すると、画面に「送信しました」と出て、送信履歴にも「送信済」と表示されました。
台帳にも `mail_ok: true` と記録されています。

**でも、受信箱には来ていませんでした。**

### 原因

PHPの `mail()` は、**サーバーが受け付けた時点で `true` を返します。**
相手に届いたかどうかは分かりません。

実際の原因はSPF（送信ドメイン認証）でした。

```
From: info@exdirect.net   SPF: redirect=_spf.ocnk.net   → このサーバーは許可されていない
From: info@exbridge.jp    SPF: include:_spf.heteml.jp   → 許可されている
```

送信サーバーがSPFに入っていないドメインを差出人にすると、**受信側が黙って捨てます。**
エラーも返りません。

### どう気づくか

```bash
dig +short TXT 送信元のドメイン | grep -i spf
```

そのサーバーがSPFに含まれているかを見ます。

### 教訓

**`mail()` の戻り値は「届いた」の証明ではありません。**
自分のアドレス宛に送って、受信箱を目で見るまで確認は終わっていません。

これは `vwork/VERIFICATION.md` が言っている「できましたと言う前の確認」そのものです。

## 罠2. 設定ファイルを置いたのに、値が効かない

### 何が起きたか

会社名や管理者アカウントを設定ファイルに書いたのに、**まったく反映されませんでした。**
ファイルは正しい場所にあり、中身も合っています。

### 原因

PHPの `define()` は**先勝ち**です。あとから同じ名前を定義しても、無視されます。

このとき、読み込み順がこうなっていました。

```php
require_once 'kinvoice_lib.php';     // ← ここで既定値を define してしまう
require_once 'kinvoice_config.php';  // ← もう遅い。無視される
```

### どう直したか

設定を**ライブラリの冒頭で最初に**読むようにしました。

```php
// kinvoice_lib.php の1行目付近
if (file_exists(__DIR__ . '/kinvoice_config.php')) { require_once __DIR__ . '/kinvoice_config.php'; }
// ここから下で、defined() で判定しながら既定値を置く
```

### 教訓

**「設定したのに効かない」は、たいてい順番の問題です。**
値が間違っているのではなく、読まれるタイミングが遅い。

## 罠3. 動いているのに、売り物にならなかった

### 何が起きたか

システムは完成し、本番でも動いていました。しかし**他人が使うことはできませんでした。**

- 会社名・住所・登録番号がコードに直接書いてあった
- ログインが自社専用の認証基盤に固定されていた
- ダウンロードURLのドメインが固定されていた

つまり、**クローンした人の画面に、こちらの会社名が出る**状態でした。

### 教訓

**「動く」と「他人が使える」は別です。**

自分の環境だけで検証していると、この差に気づけません。
確かめる方法は1つ：**設定を消した状態で、まっさらな場所に置いて動かしてみる**ことです。

このシステムは、実際にそれをやって直しました（`docs/03-exercises.md` の練習4で体験できます）。

## 罠4. サーバーの設定ファイルを、古い版で上書きしかけた

### 何が起きたか

`.htaccess` にリダイレクトを1行足そうとして、**手元のリポジトリにある版をアップロードしようとしました。**

直前にサーバー側の現物をダウンロードして比べたところ、**手元の版は6行足りませんでした。**

```
＋ RewriteRule ^bookorbit(/.*)?$ bookorbit.php [L,QSA]     ← 別システムのルーティング
＋ <Files "kcomic.php"> AddDefaultCharset Off </Files>      ← 別システムの文字化け対策
```

そのまま上げていたら、**関係のないシステムが2つ壊れていました。**

### 教訓

**共有されているファイルは、サーバー側が正です。**
`.htaccess`・共通の設定ファイル・共有ライブラリは、上げる前に必ず現物を落として差分を見ます。

手元にあるものが最新とは限りません。誰かが直接サーバーを触っているかもしれません。

## 罠5. 画像が汚い原因が、直感と逆だった

### 何が起きたか

ヘッダーのアイコンが潰れて見えました。「解像度が足りないのだろう」と考えるところです。

**逆でした。大きすぎたのです。**

```
使っていた画像: 760×1133 の全身画像（1.4MB）
表示サイズ    : 38×38 の丸
```

20倍に縮小したうえ、頭の部分だけを切り抜いていました。潰れて当然です。

### どう直したか

顔だけの画像から、表示サイズに合った192pxを作りました。

```
1.4MB → 13.7KB（100分の1）。しかも鮮明
```

### 教訓

**症状から原因を推測しない。実物を測る。**

「汚い＝解像度不足」は思い込みでした。画像のサイズと表示サイズを実際に見れば、
20倍の縮小をしていることはすぐ分かります。

## 罠6. 数字を読み違えて、結論を間違えた

### 何が起きたか

アクセスログを集計して「このページは6,942PV」と報告しました。

**間違いでした。** ログの列を取り違えていて、実際は「そのページ**から出ていった**クリック数」でした。
正しいPVは13,911です。

さらに、最初は**ボットを除外していませんでした。**生ログの72%がクローラーで、
「24,561PV」と読んでいた数字は、人間のアクセスではありませんでした。

### どう気づいたか

集計結果に `https://www.google.com/` が「ページ」として出てきたのが手がかりでした。
Googleは自社のページではありません。そこで、ログを書いている側のコードを読みに行きました。

```php
$line = date(...) . " | " . $ip . " | " . $url . " | " . $ref . " | " . $ua;
//                                          ^^^^ 3列目がURL、4列目が参照元
```

### 教訓

**数字を出す前に、その数字がどこから来ているかを確かめる。**

集計スクリプトは何を渡しても動いてしまいます。エラーは出ません。
おかしな値が混ざっていたら、それは列の取り違えのサインです。

## まとめ：6つに共通していること

| 罠 | 共通点 |
|---|---|
| 1. メール | **成功の表示が、成功の証明ではない** |
| 2. 設定 | 値ではなく、順番の問題 |
| 3. 売り物 | 自分の環境でしか試していない |
| 4. .htaccess | 手元が最新とは限らない |
| 5. 画像 | 症状から原因を推測した |
| 6. 数字 | 出どころを確かめずに集計した |

すべて **「確認したつもり」** です。

AIは指示すればコードを書きます。速いです。
しかし**「本当に動いたか」を確かめるのは、いまのところ人の仕事**です。
そのための手順が `vwork/VERIFICATION.md` にまとまっています。

次は `docs/03-exercises.md` で、実際に手を動かしてみてください。
